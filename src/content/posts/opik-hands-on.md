[LLM 평가 방법을 정리한 글](/posts/llm-evaluation-methods/) 끝에 [Opik](https://github.com/comet-ml/opik)을 직접 설치해서 돌려보겠다고 적어뒀는데, 그사이 다른 글을 몇 편 쓰느라 미뤄뒀다. 이번에 해봤다.

결론부터 말하면 도구 자체는 기대 이상이었고, **한국어로 쓸 때 반드시 확인해야 할 함정**을 하나 발견했다. 그 함정 이야기가 이 글의 절반이다.

## 1. 설치는 한 줄

```bash
pip install opik
```

설치된 버전은 2.2.29였다. 별도 서버 없이 SDK만으로 지표 계산이 되기 때문에, 일단 채점만 해보려면 이걸로 충분하다. 대시보드와 트레이싱까지 쓰려면 Docker로 로컬 플랫폼을 띄우거나 클라우드에 연결해야 하는데, 이번에는 지표 쪽만 봤다.

먼저 뭐가 들어 있는지 세어봤다.

```python
from opik.evaluation import metrics
names = sorted(n for n in dir(metrics) if n[0].isupper())
print(len(names))  # 64
```

64개다. 그리고 목록을 훑다가 좀 웃었는데, [지난 글에서 네 계열로 묶었던 것](/posts/llm-evaluation-methods/)이 거의 그대로 들어 있었다.

![지난번에 정리한 네 계열이 그대로 들어 있다](/opik-families.svg)

_설치 직후 쓸 수 있는 내장 지표가 64개다._

정답지와 비교하는 쪽에는 BLEU, ROUGE, BERTScore, METEOR, ChrF, Levenshtein이 있다. 모델이 채점하는 쪽에는 GEval이 이름 그대로 있고, `LLMJuriesJudge`라는 배심원단 지표까지 따로 있다. 규칙으로 못 박는 쪽은 `IsJson`, `RegexMatch`, `StructuredOutputCompliance`. 그리고 동작을 보는 쪽에는 `TrajectoryAccuracy`, `AgentToolCorrectnessJudge`, 대화 단위 지표들, 모더레이션과 프롬프트 인젝션 탐지가 있다.

직접 구현할 일이 거의 없다는 게 이 도구의 가장 큰 장점 같다.

## 2. 지난 글의 그 예제를 그대로 돌려봤다

지난 글에서 이런 예를 들었다. "프랑스의 수도는 어디야?"라는 질문에 모델이 "프랑스 수도라면 단연 파리죠"라고 답하면, 정답지가 "파리는 프랑스의 수도이다"일 때 **단어 겹침으로 채점하면 거의 0점**을 받는다고.

그때는 원리상 그렇다는 이야기였는데, 이번엔 실제로 돌려봤다. 세 가지 상황을 준비했다.

![돌려보니 정말로 0점이 나왔다](/opik-result.svg)

_아예 틀린 답이 정답 패러프레이즈보다 높은 점수를 받는다._

결과를 보고 두 가지가 눈에 들어왔다.

**하나, ROUGE가 세 경우 모두 0.000이다.** 표현까지 거의 같은 경우에도 0이 나온다. 이건 명백히 이상하다. 원인은 뒤에서 다룬다.

**둘, 이게 더 흥미로운데, 아예 틀린 답이 정답 패러프레이즈보다 점수가 높다.** BLEU는 오답에 0.119를 주고 정답 패러프레이즈에는 0.000을 줬다. Levenshtein도 오답 0.571, 정답 패러프레이즈 0.467이다.

왜 이렇게 되는지는 생각해보면 당연하다. "베를린은 독일의 수도이다"는 정답지와 **문장 구조가 같다.** "…는 …의 수도이다"라는 뼈대를 공유하니까 글자 단위로는 많이 겹친다. 반면 "프랑스 수도라면 단연 파리죠"는 뜻만 같고 구조가 완전히 다르다.

지난 글에서 참조 기반 지표의 한계를 설명하면서 "같은 뜻인데 0점이 나온다"고 썼는데, 실제로는 그보다 나쁘다. **틀린 답에 더 높은 점수를 줄 수도 있다.** 이 숫자를 보고 나니 왜 LLM 판정자 계열이 그렇게 빠르게 자리를 잡았는지가 더 선명해졌다.

## 3. 한국어에서 ROUGE가 0점인 이유

ROUGE가 전부 0인 게 계속 걸려서 파봤다. 원인은 도구가 아니라 **토크나이저**였다.

![ROUGE가 전부 0이었던 진짜 이유](/opik-tokenizer.svg)

_에러도 경고도 없이 그냥 0점이 찍힌다._

영어로 같은 테스트를 돌려보니 ROUGE가 1.0을 반환했다. 그래서 토큰을 직접 찍어봤다.

```python
from rouge_score import tokenize
tokenize.tokenize("Paris is the capital of France.", None)
# ['paris', 'is', 'the', 'capital', 'of', 'france']

tokenize.tokenize("파리는 프랑스의 수도이다.", None)
# []
```

한국어는 **토큰이 하나도 안 남는다.** ROUGE의 기본 토크나이저가 영문자와 숫자만 남기고 나머지를 버리기 때문이다. 토큰이 빈 리스트니 겹칠 것도 없고, 그래서 0점이 나온다.

무서운 건 이게 **조용히** 일어난다는 점이다. 예외도 안 나고 경고도 없다. 그냥 0.000이 찍힌다. 평가 파이프라인을 돌려놓고 "우리 모델 ROUGE가 0이네, 성능이 나쁜가 보다"라고 결론 내릴 수 있다. [바로 앞 글에서 다룬](/posts/data-rots-quietly/) 침묵하는 실패의 교과서적인 사례다.

고치는 건 어렵지 않다. `ROUGE`가 `tokenizer` 인자를 받으므로 직접 만들어 넣으면 된다.

```python
class KoreanTokenizer:
    def tokenize(self, text):
        return [t for t in text.replace(".", " ").split() if t]

metric = ROUGE(tokenizer=KoreanTokenizer())
```

공백으로 자르는 아주 단순한 방식인데, 이것만으로도 0.000이던 값이 의미 있는 숫자로 바뀐다. 표현까지 거의 같은 경우 0.667, 아예 틀린 경우 0.333이 나왔다.

다만 여기서도 정답 패러프레이즈는 여전히 0.000이었다. 토크나이저를 고쳐도 참조 기반 지표의 본질적 한계는 그대로다. **고친 건 버그지 한계가 아니다.**

제대로 하려면 형태소 분석기를 붙이는 게 맞다. 다만 그건 그것대로 의존성이 늘어나는 일이라, 자기 상황에서 어디까지 필요한지 정하고 시작하는 게 좋겠다.

## 4. 그래서 쓸 만한가

며칠 만져본 소감을 정리하면 이렇다.

**좋았던 점.** 지표가 많고, 이름이 직관적이고, 지난 글에서 정리한 계열이 거의 다 커버된다. 특히 에이전트 경로 채점과 대화 단위 지표가 내장돼 있는 게 반갑다. 이건 직접 만들면 꽤 성가신 것들이다. MIT 계열 오픈소스라 사내에서 쓰기에도 부담이 적다.

**주의할 점.** 지표마다 추가 패키지가 필요한 경우가 있다. ROUGE는 `rouge-score`를 따로 깔아야 하고, 안 깔려 있으면 그때야 알려준다. 그리고 LLM 판정자 계열은 당연히 API 키가 필요하니 비용을 생각해야 한다. 평가를 매 커밋마다 돌리면 청구서가 커진다.

**그리고 한국어.** 위에서 본 것처럼 기본 설정을 그대로 믿으면 안 된다. 이건 Opik의 잘못이라기보다 원래 지표 구현체들이 영어를 전제로 만들어졌기 때문인데, 어쨌든 우리가 확인해야 하는 몫이다.

## 5. 개인적인 견해

이번에 제일 크게 느낀 건, **평가 도구를 도입하는 것과 평가를 잘하는 건 다른 일**이라는 점이었다.

지표 64개가 들어 있는 도구를 설치하는 데는 1분이 걸렸다. 그런데 그중 무엇을 쓸지, 어떤 값을 통과 기준으로 삼을지, 나온 숫자를 믿어도 되는지는 도구가 알려주지 않는다. 오늘 겪은 것만 봐도 그렇다. ROUGE가 0이라는 걸 보고 모델을 의심할 뻔했는데 실제로는 토크나이저 문제였다.

[예전 글](/posts/ai-system-fails-outside-model/)에서 장애가 나면 모델부터 의심하지 말고 바깥부터 보라고 썼는데, 평가 지표에도 똑같이 적용되는 이야기였다. **점수가 이상하면 모델이 아니라 채점기를 먼저 의심하는 게 맞다.**

그리고 하나 더. 앞서 [앤드류 응의 스킬맵을 읽으면서](/posts/ai-engineering-skills-map/) 네 항목 전부가 결국 "무엇이 맞는지 어떻게 아는가"로 수렴한다고 썼는데, 오늘 작업이 딱 그 이야기였다. 채점기를 채점하는 일 말이다. 평가 도구를 쓰기 시작하면 검증해야 할 대상이 하나 더 늘어난다는 걸, 숫자로 확인한 하루였다.
