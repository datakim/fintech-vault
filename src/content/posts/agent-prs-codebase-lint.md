한 팀이 지난달 PR 11,000개를 프로덕션에 배포했고, 그중 되돌린(revert) PR은 0.5% 정도였다. 11월 14일 AI Engineer 채널에 공개된 발표에서 Lauren Tan이 내놓은 숫자다. 발표자는 Grok을 만드는 SpaceX 자회사 SpaceXSI(옛 xAI)에서 Grok Bot을 개발한다. SpaceXSI는 Grok을 만들면서 Cursor도 자회사로 두고 있어서, 발표에는 Cursor에서 겪은 사례와 Cursor의 기능이 자주 나온다. Grok Bot은 8월에 베타로 나온 데스크톱 앱으로, 저마다 컴퓨터를 하나씩 가진 에이전트에게 일을 맡기는 제품이다.

발표자 개인도 지난달 PR 3,000개를 올렸는데 상당수는 자는 동안 머지됐고, 여기까지 오는 데 6개월이 걸렸다고 한다. 하루에 수백 개씩 들어오는 PR을 사람이 다 읽을 수는 없으니, 발표는 리뷰 속도를 올리기보다 에이전트를 고칠 때마다 그 교정을 자동 검사로 바꿔 리뷰할 거리 자체를 줄여 가자고 한다. 발표자는 이걸 맹목적인 신뢰와 구분해서, 에이전트가 옳은 일을 하리라 믿을 수 있게 그 환경에 투자하는 일이라고 부른다.

## 1. 한 달 PR 11,000개, 되돌린 건 0.5%

팀 숫자부터 보면 지난달 배포한 PR이 11,000개이고, stable 버전은 거의 하루에 한 번 나간다. 10월 한 달 동안 PR을 한 번 이상 올린 사람은 227명으로, 맥락을 잘 모르는 채로 가끔 들러 기여하는 사람도 많다. 이 속도에서도 revert 비율은 0.5% 안팎으로 유지됐고 상대적으로는 오히려 낮아졌다. 앱 시작, 타이핑, 새 채팅 열기와 채팅 전환도 출시 때보다 빨라졌다. Grok Bot이 아직 웹 기술로 만든 Electron 앱이라 성능에 한계가 있다는 걸 감안하면 쉽지 않은 결과다.

발표자는 에이전트 환경에서 어디에 시간을 쓸지를 거꾸로 선 피라미드로 설명한다. 가장 넓은 위층은 코드 자체로, API 설계와 아키텍처, 리팩토링이 여기에 들어간다. 그 아래는 린트 규칙, 타입 시스템, 컴파일러, 테스트처럼 같은 코드에 언제나 같은 결과를 내는 결정론적 검사다. 이 두 층이 에이전트가 할 수 있는 일을 묶어 두면, 에이전트가 가장 쉬운 길을 골라도 올바른 패턴을 따르게 된다.

위에서 셋째 층은 런타임 검증과 형식 검증으로, 시스템이 지켜야 할 성질을 확인하고 에이전트가 의도를 제대로 알아들었는지 본다. 판단이 필요한 글(rules, skills, AGENTS.md)은 맨 아래 가장 좁은 층에 조금만 둔다.

![거꾸로 선 피라미드 모양으로 네 칸이 쌓여 있다. 맨 위의 가장 넓은 칸은 코드 자체로 API 설계, 아키텍처, 리팩토링이고 예시는 useEffect 금지와 main, renderer 폴더 분리다. 둘째 칸은 결정론적 검사로 린트 규칙, 타입, 컴파일러, 테스트이고 예시는 import 경계와 타이머 땜질 금지다. 셋째 칸은 검증으로 런타임 검증과 형식 검증이고 예시는 실행 영상, TLA+, Lean, Bombadil이다. 맨 아래의 가장 좁은 칸은 판단이 필요한 글로 rules, skills, AGENTS.md이며 최소한만 둔다.](/agentpr-pyramid.svg)

_발표의 신뢰 피라미드를 다시 그렸다. 넓은 칸일수록 시간을 많이 쓴다._

실무에서는 이 순서가 거꾸로 되기 쉽다. 에이전트가 실수하면 AGENTS.md에 "이렇게 하지 마" 한 줄을 더 적고, 그 파일이 몇백 줄이 될 때까지 늘려 간다. 발표자는 반대로, 교정할 때마다 그걸 결정론적 검사로 바꿀 수 있는지부터 따지라고 한다. 코드로 들어간 규칙은 매번 같은 결과를 내지만, 글로 적은 규칙은 에이전트가 읽고 해석해야 해서 결과가 그때그때 달라진다.

## 2. 에이전트는 코드베이스에 있는 걸 따라 쓴다

에이전트의 출력은 입력을 따르고, 그 입력에서 가장 큰 덩어리가 코드베이스다. 발표자는 2024년만 해도 출근하면 동료가 쓴 PR 세 개를 리뷰했는데, 지금은 그 숫자가 300개에 가깝다고 한다. 엔지니어 한 명이 에이전트 수백 개를 거느리는 셈이라, 코드가 PR 단위로 띄엄띄엄 오지 않고 끊기지 않는 흐름처럼 들어온다.

발표자는 이 상황을 정원에 빗대는데, 코드베이스에 걸어 둔 제약과 가드레일이 콘크리트 기초이고 에이전트가 쓰는 새 코드는 그 둘레로 자라는 식물이다. 우회 코드나 안티패턴, 폐기 예정 코드, 기술 부채가 남아 있으면 다음 에이전트는 그걸 이 코드베이스에서 통하는 패턴으로 보고 복제하고, 그 코드는 잡초처럼 금세 여기저기로 번진다.

내 식으로 바꾸면 손은 빠르지만 눈치로 일하는 알바생 300명이 동시에 요리하는 주방에 가깝다. 알바생은 냉장고에 있는 재료를 꺼내 쓰고 옆 사람이 하던 대로 따라 하니까, 상한 재료가 하나 남아 있으면 그게 300그릇에 들어간다. 벽에 "이 재료는 쓰지 마세요"라고 붙여 두는 것보다 그 재료를 냉장고에서 치우는 쪽이 확실하다.

## 3. 린트 규칙으로 막아 두면 리뷰에서 찾을 일이 없다

린트(lint)는 코드를 실행하지 않고 읽기만 해서 팀이 금지한 모양의 코드를 찾아내는 자동 검사기다. 워드의 맞춤법 검사기와 비슷한데, 규칙을 팀이 직접 정할 수 있다는 점이 다르다. 도구로는 JavaScript와 TypeScript에서 ESLint를, Python에서 Ruff나 Pylint를 많이 쓴다.

편집기에서는 빨간 밑줄로, PR을 올릴 때 도는 CI에서는 실패로 나타나기 때문에 규칙을 어긴 PR은 머지되지 않는다. 타입 검사가 자료형 실수를 잡고 테스트가 실행 결과를 확인한다면, 린트는 "이런 식으로는 쓰지 마"라는 코드의 모양을 잡는다.

Grok Bot 팀은 Dune이라는 자체 클라이언트 프레임워크를 만들어 이 원리를 적용했다. 발표자 말로는 기술적으로 새로울 건 없는 Electron판 Next.js 같은 틀이지만, 데스크톱 앱을 만들며 얻은 교훈을 제약과 린트 규칙으로 심어 두었다. 그 교훈 가운데 하나는, 제대로 쓰려면 미묘한 판단이 필요한 기능일수록 에이전트 손에서 땜질과 핑계가 섞인 코드, 이른바 슬롭을 쏟아 내기 쉽다는 것이었다.

React에서 부수 작업을 돌리는 useEffect가 대표적인 예로 꼽혔다. 쓸 곳이 분명히 있지만 잘못 쓰이는 경우가 훨씬 많고, 에이전트도 이걸 잘 다루지 못한다. 팀은 제품 코드에서 useEffect를 금지하고 Dune API 안쪽 몇 곳에서만 허용했다. 그 뒤로 이 종류의 문제는 코드 리뷰에서 잡을 필요가 없어졌다.

역시 Electron 앱인 Cursor에서는 에이전트가 메인 프로세스 코드를 화면을 그리는 렌더러 쪽으로 가져와 버벅임을 일으키는 일이 잦았다. Grok Bot과 Dune은 최상위 폴더를 electron-main과 electron-renderer로 나눠 폴더 구조 자체를 규칙으로 만들었다. 둘 사이의 import는 의존성 그래프 분석기와 린트 규칙이 막는다. 같은 규칙을 ESLint 기본 규칙으로 쓰면 대략 이렇게 생겼는데, 발표 화면이 아니라 설명을 위해 만든 예시다.

```js
// eslint.config.js
export default [
  {
    files: ["src/electron-renderer/**"],
    rules: {
      "no-restricted-imports": ["error", {
        patterns: [{
          group: ["**/electron-main/**"],
          message: "renderer에서 main 코드를 직접 가져오지 마세요. ipc.ts의 채널로 요청하세요.",
        }],
      }],
    },
  },
];
```

규칙을 어긴 코드를 쓰면 에이전트는 이런 메시지를 받는다.

```
src/electron-renderer/chat.tsx
  3:1  error  renderer에서 main 코드를 직접 가져오지 마세요. ipc.ts의 채널로 요청하세요.  no-restricted-imports
```

눈여겨볼 곳은 에러 메시지로, 사람에게는 경고문이지만 에이전트에게는 다음 행동을 정해 주는 지시문 역할을 한다. 왜 막혔는지와 대신 무엇을 써야 하는지를 적어 두면 에이전트가 막힌 자리에서 바로 맞는 길로 돌아간다. AGENTS.md에 같은 문장을 적어 두면 에이전트가 읽고 지킬지를 스스로 판단해야 하지만, 린트로 만들어 두면 지키지 않은 PR은 아예 통과하지 못한다.

## 4. 에이전트가 남긴 주석은 다음 에이전트의 핑계가 된다

발표에서 의외였던 대목은 에이전트가 마크다운과 주석을 다루는 방식이다. 에이전트는 문서, 코드 주석, rules, skills를 옳은 일을 하지 않은 이유를 적어 두는 자리로 쓰곤 한다. 사람이 한 번 가볍게 고쳐 준 것을 절대 어기면 안 되는 규칙처럼 과하게 받아들이는 일도 잦다.

Cursor에서 나온 사례를 보면, 에이전트들은 setTimeout, requestAnimationFrame, requestIdleCallback 같은 타이머를 빠른 땜질로 즐겨 썼다. 실제로는 VS Code의 명령형 구조와 React의 선언형 구조가 부딪히는 문제를 타이머로 덮고 있었다. 발표자는 타이머가 빠르게 만들어졌다 사라지기를 반복하면 큰 가비지 컬렉션이 자주 돌면서 앱이 버벅인다고 설명한다.

에이전트들은 땜질할 때마다 왜 이렇게 해도 되는지 정당화하는 주석을 남겼고, 그 주석을 본 다음 에이전트가 같은 땜질을 반복했다. 결국 타이머가 코드 곳곳으로 퍼졌고 앱 성능이 크게 나빠졌다.

Grok Bot 팀은 여기서 배운 걸 바탕으로 주석의 99%를 금지했다. 주석은 금방 낡고 사람은 어차피 잘 읽지 않으며, 에이전트에게는 어려운 일을 피해 갈 구멍이 된다. 무엇보다 강제할 수가 없어서, 다음 에이전트에게 하지 말라고 선의로 적어 둔 주석도 믿을 근거가 되지 못한다. 지금은 그 자리를 린트 규칙이 맡고, 규칙의 에러 메시지가 땜질 대신 근본 원인을 고치라고 안내한다.

팀은 에이전트를 교정할 때마다 그 교정을 결정론적 검사로 바꾸거나, API 설계와 아키텍처를 고쳐 그 문제가 아예 생길 수 없게 만든다. 이걸 충분히 반복하면 리뷰에서 살필 항목이 계속 줄고, 어느 순간 더 볼 게 남지 않아 에이전트가 PR 대부분을 스스로 머지하게 된다.

이미 땜질이 쌓인 코드베이스라면 순서가 중요하다. 발표는 먼저 린트 규칙으로 새로 생기는 안티패턴을 막고, 그다음 기존 패턴을 정리하라고 권한다. 규칙을 켤 때 기존 위반은 예외 목록으로 묶어 두고 그 목록을 에이전트에게 조금씩 줄여 가게 맡기면, 규칙 도입과 정리를 따로 진행할 수 있다. 한 번 막은 종류의 문제는 다시 들어오지 못하니, 코드 품질이 뒤로 밀리지 않고 한 방향으로만 좋아진다.

## 5. 리뷰는 코드 대신 증거물을 본다

검증은 에이전트를 더 자율적으로 만들고 그 결과를 믿게 해 주는 또 하나의 축이다. Grok Bot 팀의 코드 리뷰는 이제 상당 부분 검증 결과물을 보는 일로 바뀌었다. 에이전트가 남긴 영상, 스크린샷, 다이어그램, 형식 검증 결과가 그 대상이다.

가장 기본은 런타임 검증으로, 에이전트가 코드를 직접 실행하고 Chrome DevTools Protocol처럼 사람 개발자가 쓰는 디버깅 도구를 쓸 수 있게 해 준다. 이 검증용 스킬에 들어 있는 feature map은 사용자 관점에서 앱에 있는 기능을 사이트맵처럼 늘어놓은 목록이다. 사람이 "왼쪽 사이드바에 있는 그거"라고 말해도 에이전트가 추측할 필요가 없고, 사람과 에이전트가 같은 이름으로 기능을 부르게 된다.

앱을 띄우고 조작하는 전용 CLI도 만들어 스킬에 넣어서, 에이전트가 검증할 때마다 조작 코드를 새로 짜는 대신 이 CLI를 불러 쓰게 했다. 그만큼 토큰이 덜 들고 CLI 자체도 테스트할 수 있다.

최근에는 형식 검증도 쓰기 시작해서, 여러 기기와 플랫폼에 걸친 알림처럼 큰 사용자 흐름은 TLA+로 모델 체킹한다. TLA+는 시스템이 거칠 수 있는 상태를 모두 펼쳐 놓고 원하는 성질이 깨지는 경우가 있는지 찾는 명세 언어다. Lean은 증명을 컴퓨터가 검사해 주는 언어로, 팀이 직접 만든 가상화 라이브러리에 쓴다. 긴 목록에서 화면에 보이는 부분만 그리는 라이브러리인데, 깜빡이거나 떨리는 문제가 없다는 걸 Lean으로 증명한다. 이렇게 해서 이미 버그를 꽤 찾았지만 만능은 아니어서, 에이전트 환경의 여러 층 가운데 하나로 다룬다.

UI에는 Antithesis가 공개한 Bombadil로 속성 기반 테스트를 돌린다. 앱을 스스로 돌아다니며 "이 조건은 항상 지켜진다" 같은 성질을 확인하는 방식인데, 여기서도 UI 버그가 몇 개 나왔다.

발표자가 인용한 Cindy라는 개발자는 반년 전만 해도 미묘한 버그가 머지되는 탓에 에이전트를 믿을 수 없다고 했다. 지금은 하루 토큰의 70%를 검증에 쓴다고 하고, 발표자 역시 토큰 대부분을 검증에 쓴다. 여기 나온 기법은 모두 예전부터 있던 소프트웨어 공학 도구인데, 이해하고 작성하고 유지하는 비용이 커서 잘 쓰지 못했을 뿐이다. 에이전트가 그 비용을 크게 낮춘 덕에 발표자는 지금을 테스트와 검증의 황금기라고 부른다.

이렇게 모아 보면 PR 하나가 지나가는 길은 아래와 같다.

![PR이 지나가는 다섯 단계. 에이전트가 PR을 올리면 린트, 타입, 테스트로 된 자동 검사를 거치고, 실패하면 자동으로 반려된다. 통과하면 에이전트가 앱을 직접 띄워 영상과 스크린샷을 남기는 실행 검증을 거치고, 사람은 코드보다 증거물을 확인하며, 볼 게 없으면 자동 머지된다. 사람 확인 단계에서 자동 검사 단계로 돌아가는 점선 화살표에는 사람이 잡은 문제는 다음부터 자동 검사에서 걸리게 바꾼다고 적혀 있다.](/agentpr-flow.svg)

_발표 내용을 PR 한 건의 흐름으로 다시 정리했다. 점선 화살표가 리뷰할 거리를 줄여 가는 고리다._

자동화는 이런 기초가 갖춰진 다음에 얹는다. 지금은 새 릴리스를 만들 때마다 Grok Bot이 Cursor 프로젝트를 새로 띄우고, 그 안의 에이전트들이 앱 전체를 실제 사용자처럼 쓰면서 퍼징한다. 그렇게 찾은 버그마다 수정 PR을 열고 자동 머지까지 한다. 순서를 거꾸로 해서 슬롭을 만드는 루프를 그대로 자동화하면 슬롭이 더 많이 쏟아지고, 그걸 덮느라 토큰만 계속 늘어난다는 게 발표의 경고다.

## 6. 데이터·금융 코드에 옮기면

같은 원리를 모델링과 금융 코드에 적용하면 가장 먼저 손댈 곳은 돈과 시간이다. 금액을 float로 계산하면 반올림 오차가 쌓이니, 금액은 Money 같은 전용 타입으로만 다루게 하고 그냥 숫자를 넣으면 타입 검사에서 걸리게 한다. useEffect를 Dune 안에서만 쓰게 한 것과 같은 구조로, 다루기 어려운 계산은 한 곳에 감싸 두고 나머지 코드에는 쉬운 길 하나만 남긴다.

시간 쪽에서 신용평가 모델의 흔한 사고는 학습할 때 그 시점에는 알 수 없던 정보를 쓰는 데이터 누수다. 피처 코드가 현재 시각을 직접 읽지 못하게 막고 기준일을 인자로 받게 하면, 이런 실수가 들어올 자리가 줄어든다. 이런 팀 고유의 금지 패턴은 Semgrep처럼 규칙을 직접 쓸 수 있는 도구로 막고, 에러 메시지에는 대신 쓸 함수를 적어 둔다. 아래는 개념을 보여 주려고 단순화한 예시라, 실제로는 팀 코드에서 쓰는 시각 함수를 모두 넣어야 한다.

```yaml
rules:
  - id: no-wall-clock-in-features
    languages: [python]
    severity: ERROR
    paths:
      include: ["features/"]
    pattern-either:
      - pattern: datetime.datetime.now(...)
      - pattern: datetime.date.today()
      - pattern: pandas.Timestamp.now(...)
      - pattern: pandas.Timestamp.today(...)
      - pattern: time.time()
    message: "피처 코드에서 현재 시각을 직접 읽지 마세요. as_of 인자를 받아 asof.py의 함수로 계산하세요."
```

폴더 경계는 import-linter로 잡는다. features, models, serving을 나누고 서빙 코드가 연구용 노트북 유틸을 가져오지 못하게 막아 두면, 에이전트가 실험 코드 한 줄을 운영 경로로 끌고 들어오는 일을 리뷰 전에 걸러 낼 수 있다. 검증 쪽에서는 pandera로 입출력 데이터의 스키마를 강제하고, 모델을 바꾸는 PR에는 코드 차이 대신 기간별 KS나 승인율 변화 같은 백테스트 결과를 증거물로 붙인다.

## 7. 개인적인 견해

11,000이라는 숫자보다 오래 남는 건 교정을 검사로 바꾸는 습관이다. 자동 머지는 그 습관을 몇 달 쌓은 끝에 얻은 결과인데, 처음부터 목표로 잡으면 순서가 뒤집힌다. Dune에 들어간 규칙들도 Cursor에서 렌더러 버벅임과 타이머 땜질을 직접 겪은 사람들이 만들었다. 사람의 전문성이 사라졌다기보다, 리뷰 코멘트에 담기던 전문성이 규칙과 API로 자리를 옮겼다고 보는 게 맞다.

숫자는 조금 걸러 들을 필요가 있는데, PR 수와 revert 비율은 발표자 팀이 직접 밝힌 값이고 revert 비율이 곧 버그 비율도 아니다. 문제가 생겨도 되돌리지 않고 수정 PR로 고치는 경우가 많다. 릴리스마다 퍼징으로 찾은 버그를 수정 PR로 자동 머지하는 구조라면, 11,000개 안에는 버그를 고친 PR도 상당수 들어 있을 가능성이 크다. 그래도 PR이 이만큼 늘어나는 동안 앱 성능이 나빠지지 않고 좋아졌다는 점은 꽤 강한 근거라고 본다.

금융 코드에 가져올 때는 선을 하나 긋고 싶다. 데스크톱 앱이라면 0.5%의 revert는 다음 날 릴리스로 수습할 수 있다. 결제나 한도, 정산처럼 돈이 움직이는 코드에서는 오류 한 번이 고객 손실과 민원으로 바로 이어진다. 이런 경로는 검사와 증거물을 다 갖춘 뒤에도 사람의 승인 단계를 남겨 두는 게 맞다. 다만 그 사람이 읽는 대상은 코드 한 줄 한 줄보다 검사 결과와 증거물이어야 한다.

얼마 전 다룬 [리스크관리부 이야기](/posts/agent-bank-risk-function/)도 같은 구조였다. 그 글에서는 결정을 하나하나 승인할 수 없게 된 2선이 결정을 만드는 구조와 기록을 관리하는 쪽으로 옮겨 가야 한다고 봤다. PR을 하나하나 읽을 수 없게 된 개발 팀도 같은 길을 가는 중이다.

이번 주에 에이전트에게 같은 지적을 두 번 했다면, 그 지적을 AGENTS.md에 한 줄 더 적는 대신 에러 메시지가 달린 린트 규칙 하나로 바꿔 보는 데서 시작하면 된다.
